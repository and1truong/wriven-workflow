# Benthos / Redpanda Connect / Bento — research notes for a new TS stream processor

All sources read 2026-11-03. "RPC" = Redpanda Connect docs (docs.redpanda.com/redpanda-connect), "Bento" = warpstreamlabs.github.io/bento. Items marked **unverified** were not confirmed from an official page.

## 1. Delivery guarantees and the transaction model

- Core statement (RPC delivery-semantics guide): every batch read from an input carries an `ack()` callback supplied by the input; "It's the output's job to call the `ack()` function" to report success or failure. On a nack the *input* decides: auto-retry, propagate upstream (e.g. Pub/Sub nack), or drop. "When connecting to at-least-once inputs and outputs, Redpanda Connect guarantees at-least-once delivery without having to persist messages during transit." "Duplicates may occur during failure recovery, as is typical of at-least-once systems." No disk checkpointing is needed because delivery status flows back to the input.
  Source: https://docs.redpanda.com/redpanda-connect/guides/delivery_semantics (2026-11-03)
- Buffers page restates the rule: an input message is not acknowledged (offset not committed) until it is "either intentionally deleted or successfully delivered to all outputs"; buffers "modify (or disable) the transaction model".
  Source: https://docs.redpanda.com/redpanda-connect/components/buffers/about/ (2026-11-03)
- Bento says the same: "transaction based resiliency with back pressure, so when connecting to at-least-once sources and sinks it's able to guarantee at-least-once delivery without needing to persist messages during transit." Source: https://warpstreamlabs.github.io/bento/docs/about (2026-11-03)
- Plugin API (MIT core, redpanda-data/benthos `public/service/input.go`): `type AckFunc func(ctx context.Context, err error) error`; `Read(ctx) (*Message, AckFunc, error)`; `ReadBatch(ctx) (MessageBatch, AckFunc, error)` — the ack fn is called "once the entire batch can be either acked (successfully sent or intentionally filtered) or nacked". "The AckFunc will be called for every message batch at least once, but there are no guarantees as to when this will occur." => **a batch is acked as a single unit at the input**; there is no partial ack of an input batch.
  Source: https://raw.githubusercontent.com/redpanda-data/benthos/main/public/service/input.go (2026-11-03)
- Partial *failures* are expressible on the output side: `service.BatchError` ("NewBatchError creates a BatchError that can be returned by batched outputs. A headline error must be supplied which will be exposed when upstream components do not support granular batch errors"; `Failed(i, err)`: "If Failed is not called then all messages are assumed to have failed. If it is called at least once then all message indexes that aren't explicitly failed are assumed to have been processed successfully"). `WalkMessagesIndexedBy(indexer, fn)` maps indexes back through processor reorderings. Consumers of this: the `fallback` output ("makes a best attempt at inferring which specific messages of the batch failed"; if it can't, "the whole batch is passed to the next tier in order to preserve at-least-once delivery guarantees").
  Sources: https://raw.githubusercontent.com/redpanda-data/benthos/main/public/service/errors.go ; https://docs.redpanda.com/redpanda-connect/components/outputs/fallback/ (2026-11-03)
- Processor error: "All processing errors result in the messages being flagged as failed" — the message continues, "mostly unchanged, except for the addition of a metadata flag". Unhandled errors flow to the output stage; by default an errored message is still *delivered* (and acked) unless you filter/reject it.
  Sources: https://docs.redpanda.com/redpanda-connect/components/processors/about/ ; https://docs.redpanda.com/redpanda-connect/configuration/error_handling/ (2026-11-03)
- Tools: `try` (skip remaining processors for failed msgs), `catch` (run only on failed msgs; "When messages leave the catch block their fail flags are cleared"), `switch` with `check: errored()` (keeps flag), `mapping: root = if errored() { deleted() }` (drop => acks upstream), `reject_errored` output (errored msgs are nacked; nack-capable inputs like NATS/AMQP get a nack, "sequential inputs such as files or Kafka" => "the messages will simply be reprocessed from scratch"), `reject` output (rejects *all* messages "as though the output destination failed to publish them", string interpolates `${! error() }`), `fallback` DLQ with `@fallback_error` metadata.
  Sources: error_handling page above; https://docs.redpanda.com/redpanda-connect/components/processors/try/ ; .../processors/catch/ ; .../outputs/reject_errored/ ; .../outputs/reject/ (2026-11-03)
- RPC-only: `error_handling.strict: true` (>= 4.98.0) makes errors terminal: failed messages skip remaining processors and are nacked at the output; standalone `catch` can't recover them; use `try_catch` and `retry`. Bento's error_handling page has no strict mode. Sources: RPC error_handling page; https://warpstreamlabs.github.io/bento/docs/configuration/error_handling (2026-11-03)
- Output retries propagate to input: on output failure the input either nacks (AMQP) or "will be reattempted indefinitely with the commit withheld until success" (Kafka). Source: https://docs.redpanda.com/redpanda-connect/components/outputs/about/ (2026-11-03)
- **unverified**: whether `reject_errored` nacks a whole input batch when only one message in it errored (docs describe per-message behaviour only; given single AckFunc per batch, whole-batch nack is the likely mechanism).

## 2. Fan-out (`broker` output) and `switch` output

- `broker` patterns (identical in RPC and Bento):
  - `fan_out` (default): all outputs get every message in parallel; back pressure on one blocks all; a failed send "will be retried continuously until completion or service shut down" — designed "to prevent one bad output from causing a larger retry loop" (i.e. the *other* outputs are not re-sent; the input ack waits).
  - `fan_out_fail_fast`: like fan_out but no retry — error goes back to the input; warning: "busy retry loops could result in unlimited duplicates being introduced into the non-failure outputs."
  - `fan_out_sequential`: "an output is only written to once the preceding output has confirmed receipt of the same message"; same retry rule as fan_out. `fan_out_sequential_fail_fast`: same duplicate warning.
  - `round_robin`: one output per message in order; "If an output fails to send a message then the message will be re-attempted with the next input [sic: output]".
  - `greedy`: outputs "claim messages" as they are able; faster outputs take more.
  - `broker` also has its own `batching` block.
  Sources: https://docs.redpanda.com/redpanda-connect/components/outputs/broker/ ; https://warpstreamlabs.github.io/bento/docs/components/outputs/broker (2026-11-03)
- Ack propagation: the input's single ack is only called after *all* broker children acked (that is the transaction model). With `fan_out` the failing child is retried in place, so no duplicates to healthy children; with `*_fail_fast` the input is nacked/redelivered and **all** children receive the message again => duplicates on the healthy outputs (explicitly documented).
- `switch` output: `cases[].check` (Bloblang bool; empty = always), `cases[].continue` (test next case too), `retry_until_success` (default `false`): "If a selected output fails to send a message this field determines whether it is reattempted indefinitely. If set to false the error is instead propagated back to the input level" and "it is usually best to set this to true in order to avoid duplicate messages being routed to an output." `strict_mode` (default `false`): unmatched messages are dropped (acked); if true they are "nacked and/or reprocessed depending on your input."
  Source: https://docs.redpanda.com/redpanda-connect/components/outputs/switch/ (2026-11-03)
- `fallback` output: try children in order; on failure the next child receives metadata `fallback_error`; partial-batch inference as in §1.
  Source: https://docs.redpanda.com/redpanda-connect/components/outputs/fallback/ (2026-11-03)

## 3. `workflow` and `branch` processors

- `branch`: `request_map` ("how to create a request payload suitable for the child processors"; empty => "exact copy of the origin message (including metadata)"; `root = deleted()` => branch skipped), `processors`, `result_map` ("how the resulting messages ... should be mapped back into the original payload"; empty => origin unchanged). Failure rules, verbatim: "If the `request_map` fails the child processors will not be executed." "If the child processors themselves result in an (uncaught) error then the `result_map` will not be executed." "If the `result_map` fails the message will remain unchanged." The message is left flagged errored for standard error handling. Child metadata is not copied back unless result_map does `meta = metadata()`. Constraint: "the resulting batch must match the size and ordering of the input batch, therefore filtering, grouping should not be performed within these processors."
  Source: https://docs.redpanda.com/redpanda-connect/components/processors/branch/ (2026-11-03)
- `workflow`: a DAG of named branches. `order: [[A],[B,C],[E],[D,F]]` = explicit tiers; branches in a tier run in parallel, tiers sequentially. If `order` omitted, "a best attempt is made to determine a dependency tree between branches based on their request and result mappings" (reads vs writes of paths); a circular dependency => "the processor will fail". `branch_resources` lets resource branches join the DAG. `meta_path` (default `meta.workflow`) records `succeeded`, `skipped`, `failed` (branch name -> error string); on replay existing meta is used "to determine which branches have already been performed on the message (or skipped)"; old object kept at `<meta_path>.previous`; `<meta_path>.apply` array = explicit allow-list of stages. If `meta_path` is empty the processor "adds a general error flag to messages when any executed branch fails" (otherwise the message is NOT flagged — you query `this.exists("meta.workflow.failed.foo")`). A failed branch does not automatically skip dependents; the docs' pattern is a `request_map` that returns `deleted()` unless the upstream result exists.
  Sources: https://docs.redpanda.com/redpanda-connect/components/processors/workflow/ ; https://warpstreamlabs.github.io/bento/docs/components/processors/workflow (2026-11-03)

## 4. Batching

- Policy fields: `count`, `byte_size` (ignores metadata), `period` (Go duration), `check` (Bloblang; flush when adding a message makes it true), `processors` (run on the batch at flush; "All resulting messages are flushed as a single batch"). Flush when *any* condition is met. Defaults in outputs: `count: 0, byte_size: 0, period: "", check: ""` (all disabled).
  Source: https://docs.redpanda.com/redpanda-connect/configuration/batching/ ; https://docs.redpanda.com/redpanda-connect/components/outputs/kafka/ (2026-11-03)
- Placement: outputs with a `batching` block; some inputs (Kafka) expose `batching` because they must be consumed sequentially; `broker` input/output can batch across children; `memory` buffer has `batch_policy` (`enabled` plus same fields). "A batch policy has the capability to _create_ batches, but not to break them down" => use `split` first for pre-batched input. On shutdown "any remaining messages waiting for a batch to complete will be flushed down the pipeline."
  Sources: batching page; https://docs.redpanda.com/redpanda-connect/components/buffers/memory/ (2026-11-03)
- `split` (`size` default 1, `byte_size`): breaks a batch into smaller batches, remainder emitted as its own batch. `archive` (`format`: binary|concatenate|json_array|lines|tar|zip): batch -> one message, "adopts the metadata of the _first_ message part". `unarchive`: one message -> several, "kept in the same batch", replace the original in place; failures stay in the batch flagged; metadata copied to children (+ `archive_filename` for tar/zip, `archive_key` for json_map).
  Sources: https://docs.redpanda.com/redpanda-connect/components/processors/split/ ; .../archive/ ; .../unarchive/ (2026-11-03)
- Ack interaction (derived from §1 API, not stated on these pages): the input ack belongs to the *original* read batch; processors may split/merge/filter, but all descendants still map back to that one ack — so the input is acked only when every output batch derived from it has succeeded, and a drop (`deleted()`) counts as success. `BatchError` + `Indexer` exist precisely because processors reorder/resize batches. Note the `retry` processor doc: for batch-aware retries, `archive` the batch first and `unarchive` after.
  Sources: input.go / errors.go above; https://docs.redpanda.com/redpanda-connect/components/processors/retry/ (2026-11-03)
- Bloblang helpers `batch_index()` (zero-based) and `batch_size()`. Source: https://docs.redpanda.com/redpanda-connect/guides/bloblang/functions/ (2026-11-03)

## 5. Shutdown

- Shutdown starts when inputs have a logical end and "the final message has been processed", or on `SIGINT`/`SIGTERM`.
- `shutdown_delay` (default `""`): "delay the start of the shutdown procedure" so metrics/traces can be scraped; "the HTTP metrics endpoint continues to be available ... any active tracers are free to flush"; a second signal interrupts the delay.
- `shutdown_timeout` (default `20s` in the full example config): "sets a hard deadline ... to gracefully terminate. If this duration is exceeded then the process is forcefully terminated and any messages that were in-flight will be dropped." Takes effect after `shutdown_delay`.
- Within the timeout the drain is: inputs stop, pending batches are flushed, outputs finish in-flight; un-acked messages are never acked, so at-least-once sources redeliver them after restart (e.g. `system_window`: a partial window's messages "will be nacked such that they are re-consumed the next time the service starts").
  Sources: https://docs.redpanda.com/redpanda-connect/configuration/about/ ; https://warpstreamlabs.github.io/bento/docs/configuration/about ; https://docs.redpanda.com/redpanda-connect/components/buffers/system_window/ (2026-11-03)

## 6. Backpressure and buffers

- "Redpanda Connect outputs apply back pressure to components upstream": if the sink blocks, consumption pauses. Mechanism is the transaction model: an input can only have a bounded number of un-acked batches outstanding (output `max_in_flight`, e.g. Kafka default 64: "The maximum number of messages to have in flight at a given time"); `pipeline.threads` (-1 = logical CPUs) bounds processor parallelism. For strict ordering Kafka docs require `max_in_flight: 1` + `retry_as_batch: true`.
  Sources: https://docs.redpanda.com/redpanda-connect/components/outputs/about/ ; .../outputs/kafka/ ; https://docs.redpanda.com/redpanda-connect/configuration/processing_pipelines/ (2026-11-03)
- Buffers sit "immediately after the input layer" and can "intentionally weaken the delivery guarantees". Types: `none` (default), `memory`, `sqlite`, `system_window`.
- `memory`: `limit` default 524288000 bytes; "consumption will be stopped with back pressure upstream if the total size of messages in the buffer reaches this amount"; "This buffer intentionally weakens the delivery guarantees of the pipeline" and "should never be used in places where data loss is unacceptable" => input is acked on buffer write, so a crash loses buffered data (at-most-once for the buffered segment).
- `system_window` (beta): tumbling/sliding windows on the system clock; `timestamp_mapping` (default `root = now()`), `size`, `slide`, `offset`, `allowed_lateness`; keeps the transaction model (acks on delivery), but late messages for expired windows are dropped; sliding windows deliver a message multiple times, "only the first delivery is acked or nacked as normal"; under back pressure "windows older than the current and last ... will be dropped".
  Sources: https://docs.redpanda.com/redpanda-connect/components/buffers/about/ ; .../buffers/memory/ ; .../buffers/system_window/ (2026-11-03)
- Caveat on external state (dedupe cache written before delivery can turn a retry into a drop): keep dedupe state in-process or make sinks idempotent. Source: delivery_semantics guide (2026-11-03)

## 7. Streams mode, CLI, tests

- Streams mode: one process runs "multiple entirely isolated streams" (each with input/buffer/pipeline/output); `rpk connect streams -r "./prod/*.yaml" -o ./config.yaml` (or `bento streams`); `-o/--observability` = shared root config (http, logger, metrics, tracing); resources are shared across streams; stream HTTP endpoints are prefixed `/<stream_id>/...` (`--prefix-stream-endpoints=false` disables). Metrics get a `stream` label. REST API disabled by default since RPC 4.111.0; enable with `--bind-http`.
  Sources: https://docs.redpanda.com/redpanda-connect/guides/streams_mode/about/ ; .../using_rest_api/ ; https://warpstreamlabs.github.io/bento/docs/guides/streams_mode/using_rest_api (2026-11-03)

API-created configs get function interpolation but "do _not_ benefit from environment variable interpolation". `/resources/...` and `/ready` are mentioned in the about page / **unverified** exact paths.

Can be used multiple times", `-r/--resources`, `-e/--env-file`, `-t/--templates`, `-w/--watcher`, `--chilled` = run despite lint errors, `--log.level`), `lint` (exit 1 on errors; `--deprecated`, `--labels`, `--skip-env-var-check`), `echo` (print normalised config with env resolved), `create [in/proc/out]` (e.g. `create stdin/bloblang,awk/nats`; `--small`), `list` (`--format text|json|cue`; `jsonschema` for bloblang-functions/methods), `dry-run` (exit 1 on connection errors), `blobl`, `test`, `template`, `streams`, `plugin`, `mcp-server`, `agent`. - Unit tests: file `foo_benthos_test.yaml` (RPC) / `foo_bento_test.yaml` (Bento), or inline `tests:` at the end of the config. ## 8. `error()` / `errored()` and `catch`

- Bloblang: `errored()` "Returns true if the message has failed processing, false otherwise." `error()` "Returns the error message string if the message has failed processing, otherwise `null`." Plus `error_source_label()`, `error_source_name()`, `error_source_path()` (component that caused the error; `null` if no error).
  Source: https://docs.redpanda.com/redpanda-connect/guides/bloblang/functions/ (2026-11-03)
- `catch` = `for_each` over only failed messages, then clears flags; typical: `catch: [ { log: { message: "${! error() }" } }, { mapping: "root = deleted()" } ]`. A `try` nested inside a `catch` won't run unless flags are cleared first (`catch: []` trick). Source: processors/try, processors/catch pages (2026-11-03)
- Processor `retry`: `backoff.initial_interval` 500ms, `max_interval` 10s, `max_elapsed_time` 1m (0s = unbounded), `max_retries` 0 (= unbounded, >= 4.31.0), `parallel` false, `processors[]`; per-message, not per-batch; after exhaustion "these errored messages will proceed through to the next processor". Source: https://docs.redpanda.com/redpanda-connect/components/processors/retry/ (2026-11-03)

## 9. Retry/backoff shape on outputs

- Common output shape (e.g. `kafka`): `max_in_flight` (64), `max_retries` (0 = "no discrete limit"), `backoff: { initial_interval: 3s, max_interval: 10s, max_elapsed_time: 30s }`, `batching: {...}`. Source: https://docs.redpanda.com/redpanda-connect/components/outputs/kafka/ (2026-11-03)
- `retry` output wrapper: `output` (child), `max_retries` 0, `backoff.initial_interval` 500ms, `max_interval` 3s, `max_elapsed_time` 0s; message "retried either until success or, if the retries or max elapsed time fields are non-zero, either is reached"; when exhausted the error propagates to the input (which then redelivers) — for a DLQ use `fallback`. Source: https://docs.redpanda.com/redpanda-connect/components/outputs/retry/ (2026-11-03)
- Design consequence: exponential backoff with (initial, max, elapsed, count) is the uniform vocabulary across processors, outputs and wrappers.

## Design lessons for a small core

1. Make the unit of delivery a *batch with one ack function* (`ack(err?)`); everything downstream (split/merge/filter/fan-out) must resolve back to that single ack; a batch is acked only when all derived outputs succeed or the messages were deliberately dropped.
2. Model processor errors as a per-message flag (`errored`, `error`, `error_source`) that travels with the message instead of exceptions; keep `try`/`catch`/`switch(errored())`/`deleted()` as the only four error primitives.
3. Offer an opt-in strict mode (errors terminal => nack) like RPC 4.98+, but keep the default "flag and continue" because it composes with DLQs.
4. Fan-out default must retry the failing child in place (RPC `fan_out`) so the input ack waits; expose the `fail_fast` variant only with a loud duplicate warning. Same for `switch.retry_until_success` (prefer default `true` in a new design).
5. Represent output partial failures as an indexed `BatchError` (headline + per-index errors; "no Failed() call = all failed") so wrappers (`fallback`, retry) can re-send only the failed subset without losing at-least-once.
6. Backpressure = bounded un-acked batches: `max_in_flight` on outputs and bounded worker count on the pipeline; no queues between stages unless a buffer is explicitly configured.
7. Buffers are a separate, optional stage that *changes* guarantees; the memory buffer should ack on enqueue and carry a documented data-loss caveat; a windowing buffer should keep the ack chain.
8. One backoff vocabulary everywhere: `{ initial_interval, max_interval, max_elapsed_time, max_retries }` with 0 = unbounded.
9. Batching policy = `{count, byte_size, period, check, processors}`; flush on any condition; flush pending batches on shutdown; a policy creates batches but never splits them (provide `split`).
10. DAG-of-branches (`workflow`) only needs: named branches with `request_map`/`result_map`, dependency inference from read/write paths with an explicit `order` override, parallel tiers, and a structured `meta.workflow.{succeeded,skipped,failed}` record (replayable via `apply`/`previous`).
11. Shutdown: `shutdown_delay` (observability grace) then `shutdown_timeout` hard deadline; never ack on timeout — drop and let the source redeliver.
12. Ship the ergonomics that made Benthos pleasant: `lint` (exit 1), `echo` (normalised config), `--set path=value`, `list --format json|cue`, and a YAML unit-test format (`input_batch` -> `output_batches` with `json_equals`/`content_equals`/`bloblang`/`metadata_equals`, `mocks`).
